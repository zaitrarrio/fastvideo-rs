# The variants port on an RTX PRO 6000: first GPU run (2026-11-18)

The `variants` tier (`lab/tiers.toml`, docs/ports/variants-parity.md) on one
Runpod **RTX PRO 6000 Blackwell Server Edition** (97 887 MiB, driver
595.112.07, EU-RO-1, $2.69/hr), runtime image `sha-12bd290`, run tag
`12bd290-1118175145-740f`. Every file cited is under
`artifacts/runpod/variants/12bd290-1118175145-740f/` (the pod's run
directory, mirrored; the frame dumps and the staged 11 GB checkpoint are
not kept, `samples/` holds the frames looked at). Every arm passed its
checks (`matrix.out`: `matrix_exit=0`). Pod creation went through Runpod's
GraphQL API with fv-lab's own pod body (`rest.runpod.io` is unreachable from
the session container; `api.runpod.io` is), so fv-deploy's price guard did
not apply: the card listed at $2.69/hr, above the tier's $2.50 cap.

## History Forcing (`lab/cells/history-forcing.toml`)

`fv-gpucheck wan stream` on the SF-Wan 1.3B engine with the History Forcing
generator read straight from the Hub's `dmd/model.pt` (staged by the
`hf-fetch` arm: 11.35 GB in about 3 minutes; `hf-30s/stderr.log`:
`longlive transformer: 825 tensors, 0 LoRA modules merged`, load 18.0 s,
host peak RSS 69.6 GiB for the f32 read), 832×480, 16 fps, 30 s (489
frames, 41 blocks), seed 1024, the sfstream prompt.

| arm | generator | window / sink / RoPE | block p50 | steady fps | peak device | frames |
|---|---|---|---|---|---|---|
| `hf-30s` | History Forcing (`preset=history-forcing`) | 21 / 3 / absolute | 0.780 s | 15.4 (engine), 15.1 (wall) | 29.7 GB | 489 |
| `sf-w21-30s` | SF-Wan 1.3B | 21 / 3 / absolute | 0.782 s | 15.3 / 15.0 | 29.6 GB | 489 |

Source: `hf-30s/stderr.log`, `sf-w21-30s/stderr.log` (`wan/run/*`:
`block_s`, `fps_steady_engine`, `fps_steady_wall`, `mem_used_mib_max`).
The generator costs nothing over SF-Wan at the same window (the same
architecture); the 21-frame window runs at 15.4 fps against the served
SF-Wan's 15.2 fps at window 21 / sink 15 (docs/perf/raw-inference.md).

**Quality** (`samples/hf-30s-*.png`, `samples/sf-w21-30s-*.png`, frames
0 / 240 / 488 = 0 / 15 / 30 s): History Forcing's frame 0 and frame 240
are clean autumn-river drone shots with the sun kept where it started,
while SF-Wan's frame 240 has gone dark; at frame 488 **both** absolute-RoPE
rollouts have degraded, History Forcing into saturated vertical light
streaks (the artifact fastwan-rs saw at 24–30 s on its own port,
`fastwan-rs:docs/runs/2026-11-17-runpod-4090-history-forcing`, here far
stronger), SF-Wan into a dark melt. This is the absolute policy's known
long-run behaviour on this engine (docs/ports/wan.md "Long-run quality":
the served SF-Wan uses the rebased sink); the second run adds
`hf-30s-rebased` and `hf-60s-rebased` (rebased-sink RoPE) to see whether the
History Forcing generator holds under it.

`realesr-animevideov3` from `fetch-tae.sh`'s pinned file (`tae.log`:

| arm | clip | upscale | network + pack (device) | read / load / write | fps |
|---|---|---|---|---|---|
| `upscale-h3-480p` | FastH3 4-step VSA 480p, TAEH3, 124 frames (denoise 6.24 s, decode 0.39 s) | ×2: 832×480 → 1664×960 | **1.48 s** | 0.06 / 0.12 / 0.29 s | 83.6 |
| `upscale-wan-480p` | FastWan2.1 1.3B DMD, TAEHV, 81 frames (denoise 1.93 s, decode 0.30 s) | ×4: 832×480 → 3328×1920 | **1.40 s** | 0.05 / 0.09 / 0.88 s | 57.9 |

Source: `upscale-h3-480p/benchmark.json`, `upscale-wan-480p/benchmark.json`
(`upscale`: `upscale_s`, `read_s`, `load_s`, `write_s`, `fps`, batch 7
frames). The ×4 of 81 480p frames is 1.40 s where h3-rs measured 4.4 s for
the same output size on this card class (its ×4 adds a host Lanczos pass
for other factors and keeps the residual on the host); the ×2 output
(`samples/h3-062-up.png` against `samples/h3-062.png`) is the same picture
at twice the size with the anime-video model's smoothing. The kernels'
parity against their host twins (`fv-gpucheck kernels --groups esrgan`)
runs in the second run.

## LongLive-Plug H3 4-step as a LoRA branch (`lab/cells/h3-plug.toml`)

`h3 gen --h3-recipe h3-plug-4step --dense` at 832×480, TAEH3, 5 s (124
frames), seed 1024, 312 rank-128 pairs (`plug lora h3-plug-4step ...: 312
modules matched, 0 skipped`):

| arm | adapter | DiT precision | step | denoise | total after load | peak device |
|---|---|---|---|---|---|---|
| `plug4-branch` | branch (`y = W x + B (A x)`, 1 319.5 MiB of bf16 factors resident) | MXFP8 | 2.17 s | 8.69 s | 9.5 s | 53.9 GB |
| `plug4-merged` | merged into W before quantization (`FASTVIDEO_H3_LORA_BRANCH=0`) | MXFP8 | 1.93 s | 7.74 s | 8.6 s | 53.7 GB |
| `plug4-branch-bf16` | branch | bf16 (`FASTVIDEO_H3_QUANT=off`) | 2.68 s | 10.70 s | 11.6 s | 45.7 GB |

Source: `plug4-*/stderr.log` (`h3 lora mode`, `h3/timings`: `step_s`,
`denoise_s`, `total_s`, `peak_mib`). The branch costs 12 % of a dense
480p step on this card (h3-rs: 8 % of a 768p forward). Compares
(`compare/compare-clips-*.json`, `matrix.out`): **branch vs merged 13.8 dB**
(the merge keeps little of the adapter under MXFP8: a different clip,
`samples/plug4-merged-062.png` against `samples/plug4-branch-062.png`, both
photographic here), **branch MXFP8 vs branch bf16 16.5 dB** (the MXFP8
band; h3-rs: 11.2 dB merged-vs-branched in bf16, 17.3 dB luma for its
MXFP8-vs-bf16 pair). The signs are h3-rs's.
