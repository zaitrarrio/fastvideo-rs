# Fast boot: pre-quantized DiT tree (A) and ready-after-load (B)

Date: 2026-10-07. Branch `feat/fast-boot`. Owner-approved boot-time work
for serve pods. Measured on one RTX PRO 6000, EUR-IS-1, EU volume
`jg48s6o1w0`, image `fastvideo-rs-serve:h3-turbo-sha-d708c91`.

## Before

h3-turbo, `latest` b51ddcd, 2026-10-06 (docs/control/README.md §6a). Two
thirds of the boot was reading weights from the network volume at
0.6-0.8 GB/s. Of that, the DiT read 98.8 GB, merged the FastH3 Preview
adapter, folded 26 GB of AdaLN projections into the modulation table and
quantized blocks 2..=46 to MXFP8. All of that is a constant of the
checkpoint and recipe. READY then waited another 60 s for two warm-up
generations.

## A. Pre-quantized resident DiT tree

**What is stored.** The resident state of the text refiner and the DiT,
exactly as the load leaves it on the device (`crates/fastvideo-cudarc/src/h3/dit_tree.rs`):

- every linear as `Linear::snapshot` gives it: a bf16 weight, or the one
  blob a W8A8 / MXFP8 GEMM reads (`<p>.qblob`: E4M3 codes, bf16 rows of
  unquantized sections such as the VSA gate, then the swizzled E8M0 scales)
  plus `<p>.qscales` and `<p>.qlayout`;
- the bias, the norm weights and the AdaLN table as F32.

Fused projections are stored fused. The AdaLN projections are not stored:
only the table built from them is, so 26 GB are never read.

**Exactness by construction.** `fv-gpucheck quantize-dit` loads the model
as fv-serve does (same process plan and technique profile, same
`H3PipelineOptions`, quantize-at-load). It then reads every tensor back from
the device and writes it. A verify pass loads the tree and reads everything
back again, and requires the same state digest (sha256 over name, dtype,
shape and bytes of every tensor) tensor for tensor. It also requires the
file's sha256 to equal the manifest's.

**Selection at load.** `H3Pipeline::load` (`h3/pipeline.rs`) takes
`<root>/transformer_prequant_<recipe>_<quant>/` when its manifest matches
this load's identity. The identity covers:

- format and version, recipe and quantization mode;
- the VSA gate, the layer counts and the ladder's timesteps;
- the adapter's path, size and strength, and the linear route.

The source shards' names and sizes and each tree file's size must also
match. A tree that matches is read ahead in place of the checkpoint.
Anything else quantizes at load and logs the reason. Hashes are checked by
the tool and by `verify-weights.sh dit-prequant`, not at boot.

Knobs: `FASTVIDEO_H3_DIT_TREE=auto|off|require` and
`FASTVIDEO_H3_DIT_TREE_DIR=<dir>`. Recipes with no stored form fall back to
the load path: LongLive-Plug, Ref2VA, MLX affine, NVFP4 and process-wide
FP8.

**Tests.** The `dit_tree` unit tests run on sample tensors through the real
quantizer: MXFP8 with a bf16 gate section, W8A8 with three sections, and
plain bf16. Each is stored, read back, and checked for identical bytes and
identical GEMM output; the layout round trip, identity mismatch and stale
source or file rejection are tested too. On the GPU, the full model is
checked by the tool's identity check below.

## B. Ready after load, warm-up in the background

| | |
|---|---|
| backend seam | `EngineBackend::warmup_pending` / `warmup_run` (`engine-service/src/backend.rs`) |
| executor | `Warmups` (`engine-service/src/executor.rs`): runs one warm-up step when nothing is queued and no session holds the executor, on the executor thread itself, so never beside a job |
| yield | `State::yield_warmups` (`service.rs`): every submit, session open, drain or shutdown cancels the running warm-up step. The cancel lands at the step's next denoise step (the pipeline's normal cancel path, which also resets per-request state), the job runs, and the step is retried when the executor is idle again |
| state | `Warmup` in the pool: `off` / `pending` / `running` / `done` / `failed`. `/health` and `/healthz` carry `warmup` (`warming` / `warm` / `off`) and the worker status shows it. Logs say `warmup started (background)`, `warmup yielded to a job (background)` and `warmup done (background) … seconds=` |
| CUDA | the same i2v and t2v jobs as before (`cuda/backend.rs`). `warmup = true` now runs in the background. `warmup = "blocking"` or `FV_WARMUP=blocking` gives the old ready-after-warm-up; `FV_WARMUP=off` skips the warm-up (`WarmupMode`, `cuda/caps.rs`) |
| fv-control | `boottime.ts`: a `warmup_start` milestone, "(background)" labels, rows in time order |

Tests: `engine/tests/engine.rs::background_warmup_is_ready_first_and_yields_to_jobs`
covers five things:

- ready before the warm-up runs;
- a job that arrives mid-warm-up cancels the step and runs first;
- strict begin/end pairs, so no overlap;
- the warm-up resumes and completes;
- the first job's output equals the same job's output after the warm-up.

It passed 10 runs out of 10. Also covered: the config, pool and boot
timeline tests, and `scripts/serve/check.sh`.

## Other models

On RTX PRO 6000 (sm_120), no other served DiT quantizes at load:

- Wan's MXFP8 default is sm_100 only.
- LTX `ltx-pro` / `ltx-turbo` run a bf16 DiT. Only `ltx-draft` builds NVFP4
  FFNs at load (opt-in).
- The LTX-2.5 Gemma FP8 text-encoder tree already exists (E13).
