## Findings

1. **h3 presets: the r2 plan has no LoRA tree (bug; blocks every r2 h3 boot).**
   - `POOL_PRESETS` in `control/src/presets.ts` gives both `h3-turbo` and `h3-max` `weights: ["h3-base"]`.
   - On the volume, `FastH3-4-step-Preview-v1-LoRA/` sits next to `h3-base/`. In R2 it is a separate tree, so an r2
     worker never gets it.
   - fv-serve fails: "recipe 4step-vsa needs the FastH3 Preview v1 vsa-datafree adapter". h3-max's Sol-H3 recipe
     needs `dense-datafree` from the same tree (`crates/fastvideo-models/src/h3/lora.rs`).
   - The same list drives the Runpod pod and Brev plans (`r2` and `hub`), so those break the same way.
   - Fix: add `"FastH3-4-step-Preview-v1-LoRA"` (6.82 GB) to both presets' `weights`.
   - Related, slower but not broken: the plan also lacks `h3-base/transformer_prequant_*_mxfp8` and
     `h3-base/text_encoder_fp8`. The worker logged "quantizing at load (no pre-quantized form)". Adding these nested
     trees needs a check that the fetcher's rename into `h3-base/` works when a nested tree arrives first (smaller
     trees go first). That is a follow-up.
   - **Fixed in `claude/r2-fixes` (PR #76):** `h3-turbo` and `h3-max` list `FastH3-4-step-Preview-v1-LoRA`. A preset's `prequant` trees
     (`h3-base/text_encoder_fp8` for all three H3 presets, and the recipe's `transformer_prequant_*_mxfp8`) are
     fetched with r2, never from the Hub. The boot skips the MXFP8 ones below sm_100 (H100 / H200 run W8A8). The
     nested placement is tested (nested trees first, a parent already present). `src/recipe-trees.ts` lists what
     the engine reads per recipe beyond the config's `weights`, and `test/unit/preset-trees.test.ts` checks every
     preset (pods and serverless) against its config and that table against the Rust sources. The other presets
     were already complete.
2. **r2 endpoints in any DC can land on a host whose driver is too old.**
   - Worker `jxhfj2rrbqmvap` fetched, then fv-serve panicked:
     `libcuda.so: undefined symbol: cuCtxGetDevice_v2` (cudarc 0.17.8). That symbol needs a CUDA 13 driver.
   - It crash-looped twice, both times from the cache. Runpod then moved the job to a new worker, which fetched
     58 GB again. The job's delay was 830 s.
   - With the volume, workers were pinned to EUR-IS-1, whose drivers are new. `DEFAULT_CUDA = []` in
     `control/src/serverless/spec.ts` relies on that.
   - Proposed:
     - give r2 (any-DC) endpoints a CUDA filter by default, for example `allowed_cuda: ["13.0"]` plus any newer
       versions Runpod lists (the `CUDA_VERSIONS` enum stops at 13.0);
     - make the boot check the driver and exit with a clear error before fv-serve, instead of a panic.
   - **UNVERIFIED**: which of Runpod's CUDA labels the 595.x hosts carry. The `"13.0"`-only filter hid them on
     2026-10-07.
   - **Fixed in `claude/r2-fixes` (PR #76):** r2 endpoints default to `allowed_cuda: ["13.0"]` (Runpod's REST enum still ends there; the
     image needs CUDA 13, driver ≥ 580), and so do r2 pods outside EUR-IS-1. `allowed_cuda: []` lifts the filter if
     it hides too many hosts. Every boot first checks the driver (`nvidia-smi` ≥ 580 and `cuCtxGetDevice_v2` in
     `libcuda`). An old host gets `driver_too_old: …` reported to fv-control and the boot exits before any fetch.
   - **Superseded 2026-10-14 (`claude/cuda-filter-13x`):** the 595.x hosts carry the `"13.2"` label (GraphQL
     `lowestPrice`: Secure RTX PRO 6000 stock only under `"13.2"`), so `["13.0"]` hid them all, and REST refuses
     `"13.1"` / `"13.2"`. Pods and endpoints now send no exact list by default. Endpoints get
     `minCudaVersion: "13.0"`, and the driver check above keeps the minimum for pods (docs/control/serverless.md §1b).
     A pod's diagnosis treats that line, or cudarc's `undefined symbol`, as fatal and places a new pod.
3. **A 60 s stall before the fetch.**
   - On worker 1, a `curl` got 0 bytes in 60 s ("Operation timed out after 60000 milliseconds"), and the plan
     started 145 s after the container. The other two boots took 13 s.
   - The only 60 s `--max-time` in the r2 boot is the download of `r2-fetch.py` from fv-control (`--retry 5
     --max-time 60`). The remaining ~70 s before the plan is unexplained.
   - Proposed: add `--connect-timeout 10 --max-time 20` there, or ship `r2-fetch.py` in the image.
   - **Fixed in `claude/r2-fixes` (PR #76):** the serve images carry `python3`, `curl` and `r2-fetch.py`. The boot uses the image's
     fetcher when its SHA-256 is the pinned one, else downloads with `--connect-timeout 5 --max-time 30 --retry 4
     --retry-all-errors`. The image had no `python3` or `curl`, so every r2 boot ran `apt-get update && install`;
     that is the most likely cause of the other ~70 s (**UNVERIFIED**). Every step is now timed and reported.
4. **151 s between the end of the h3 fetch and the fv-serve start, with nothing logged.**
   - After its summary, r2-fetch.py only sends one report (20 s timeout). The boot then fetches the aux files
     (about 375 MB of TAE and LPIPS files) from GitHub raw and download.pytorch.org.
   - The wan boots spent 6-9 s on the same step, so the time is most likely those downloads on that host. This is
     **UNVERIFIED**.
   - Proposed: log the aux step's start and end, and serve the aux files from R2 (`auxiliary/` is already
     published there).
   - **Fixed in `claude/r2-fixes` (PR #76):** the aux files come from R2 with the trees (`auxiliary/tae`, `auxiliary/lpips`) and are then
     checked by SHA-256 (the pinned URLs remain the fallback). Each boot step (`tools`, `fetcher`, `fetch`, `aux`) is
     logged with the time of day and the seconds since start, and reported (`serverless_boots.steps`,
     `outlook.last_boot.breakdown`).
5. **Run 2 is blocked: standalone Runpod pods are EU-only, also with r2.**
   - The launch schema's `dc` is an enum of the regions that have a volume (`control/src/schemas.ts`), and
     `regionOf()` in `control/src/standalone.ts` refuses anything else.
   - r2-weights.md §4 notes this as a follow-up.
   - Proposed: when `weights_source` is `r2` (and so `volume: false`), accept any `RUNPOD_DATA_CENTERS` value.
   - **Fixed in `claude/r2-fixes` (PR #76):** a standalone launch takes any Runpod `dc` with `weights_source: r2` (the pool's new
     `data_centers`; `fv-control.sh pod launch … --weights r2 --region US-TX-3`). The volume stays EUR-IS-1 only.
6. **CLI: `endpoint invoke --async` stops polling at once.**
   - The first answer's `.job` is a number, so `jq '.job.finished_at'` errors and the `until` loop exits.
   - Fix in `scripts/serve/fv-control.sh`: test `.done` / `.status` on the first answer, and poll
     `/jobs/<n>` (`.job.finished_at`) only after that.
   - The round polled `GET /api/serverless/<ep>/jobs/<n>` directly instead.
   - **Fixed in `claude/r2-fixes` (PR #76):** the CLI polls `/jobs/<n>` until `.job` is an object with `finished_at` (integration test).
7. **Brev: the warm restart of the parked g7e.2xlarge never came up.**
   - The launch claimed `fv-pod-persist-brev1-1011200856` ("none of the trees on its disk; downloads
     fastwan22-ti2v-5b, wan22-ti2v-5b").
   - For 700 s, Brev reported it STOPPED and no host script ran. The previous warm restart reached the host script
     in 21.5 s.
   - The run was stopped at 05:28 (before the 900 s restart timeout would have created a fresh VM). fv-control
     recorded the VM as **held** (kept; "reusable from 05:43Z").
   - Cause **UNVERIFIED**: Brev capacity or the start call. It needs Brev's own view of the instance.
   - **Fixed in `claude/r2-fixes` (PR #76):** diagnostics, not a cure (the VM was not touched). fv-control used to send `PUT …/start` and
     ignore Brev's answer: it never checked the status before or after, and never read `statusMessage`. Brev's CLI
     (brev-cli `pkg/cmd/start`) starts only a STOPPED workspace whose type is stoppable, then polls until RUNNING.
     Now the warm restart reads the workspace first. It waits out STOPPING (60 s), does not start a RUNNING one
     again, and refuses anything else with Brev's status. It keeps Brev's answer to the start (status +
     `statusMessage`) in the record's note and the operation log. Every poll of the `up` wait carries Brev's
     status, message and health. A workspace still STOPPED 180 s after its start gets the start once more. After
     300 s the cron raises `brev_restart_stuck` with Brev's message.
   - Best hypothesis: Brev accepted the start but could not place the stopped `g7e.2xlarge` again. A stopped
     instance's disk ties it to its cloud zone, and the zone had no capacity. Brev reported that only in
     `statusMessage`, which fv-control did not read. A start sent while the park's stop was still STOPPING, which
     Brev may ignore, is the second candidate. The next restart's log will show which.

## Recommendation

- **`R2_DOWNLOAD_GBPS` = 0.5** (was 1.0), the median of the three measured fetches. Changed in this PR with
  r2-weights.md §5.4. An endpoint's outlook uses its own last measured rate once a boot reports one.
- **Keep `DEFAULT_SLS_WEIGHTS_SOURCE = "volume"`. Do not flip it to r2.**
  - From zero, r2 is slower end to end: wan 2-3× (279 s start → ready against 119 s).
  - h3 at 0.5 GB/s adds about 5 min to every cold start on a fresh worker, and its r2 plan is broken until
    finding 1 is fixed.
- r2 is still the way to place an endpoint outside EUR-IS-1, or when the EU has no stock. FlashBoot hides the fetch
  after the first boot of a worker.
- Revisit the default after these:
  - findings 1-4 are fixed;
  - an H3 boot completes, including its load without the prequantized trees;
  - a fetch at concurrency 64 is measured;
  - the optional per-DC cache volume (§9.4) or the FP8 / prequantized subsets (§5.4 item 2) are weighed for h3.
